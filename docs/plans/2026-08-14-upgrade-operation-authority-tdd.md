# Make the host authoritative for upgrade operations

## Context

The one-click upgrade implementation has three independent interpretations of
one operation:

- the host updater persists the operation and owns activation recovery;
- Fleet retries local Unix-socket mutations and audits their outcomes; and
- the browser reconstructs ambiguous trigger and dismissal results from the
  target version, prior operation, current server version, timestamps, and two
  session-storage records.

The browser cannot name an operation before calling `TriggerUpgrade`, even
though the host protocol already supports idempotent caller-generated UUIDs.
Terminal outcomes also lack an explicit revision: `completed_at` currently
doubles as a timestamp, remediation cutoff, and audit idempotency token.
Startup reconciliation can materially rewrite a terminal outcome while
retaining its operation id, so an old tab can acknowledge recovery guidance it
never observed.

None of the updater or one-click operation protocol has shipped in a stable
release. The supported compatibility boundary is therefore the previous stable
release to the next stable release. Intermediate RC browser, protocol, and
state formats are disposable and do not receive compatibility shims.

## Goals

- One immutable operation id identifies a trigger from the browser through
  Fleet to the host updater.
- One explicit outcome revision identifies the exact terminal result an
  operator observed and acknowledged.
- The host is the only authority for whether an operation is active, visible,
  remediated, or acknowledged.
- Fleet retains authorization, release-eligibility validation, HA lifetime
  admission, transport reconciliation, and idempotent audit ownership.
- Browser state is limited to poll/rendering state plus one authentication-
  scoped command correlation record. That record survives reload through the
  exact operation's active lifetime and clears when the host reports it
  terminal, conclusively rejects it, or an operator explicitly unlocks the
  manual fallback; operation state and terminal visibility still come
  exclusively from the host.
- The filesystem activation, forward-only recovery, privilege, and trust
  boundaries remain unchanged.

## Non-goals

- Changing download, checksum, extraction, preflight, directory-swap, fsync,
  updater self-replacement, or HA activation ordering.
- Supporting an intermediate RC updater or its unversioned persisted state.
- Combining release discovery and operation polling into one endpoint.
- Relaxing manual-fallback locking while a host mutation may be active.
- Introducing a generic workflow engine or a second database for updater
  state.

## Contract

### Operation identity

`TriggerUpgradeRequest.operation_id` is a required canonical UUID generated by
the browser before the mutation. Fleet validates it, revalidates the offered
target, and forwards the pair unchanged. Reusing the id with the same target is
idempotent; reuse with a different target is rejected.

Fleet retries only the local Fleet-to-updater boundary. If the browser loses
the Fleet response, it polls for the exact id it generated. A reachable status
response containing another id proves that the pending command was not the
current host operation; target-only and timestamp inference are forbidden.
The browser persists the pending id and target before submitting the mutation,
scoped to the current authentication session, so a reload cannot discard the
conflicting-operation lock while Fleet is still admitting or running the
command. Observing the exact active operation does not clear that correlation;
an exact terminal result does.

### Terminal outcome identity

`UpgradeOperation.outcome_revision` is zero while an operation is active. The
host increments it when it first creates a terminal outcome and whenever
startup or recovery materially rewrites that outcome. Acknowledgement does not
increment it.

`AcknowledgeUpgradeRequest` carries both the operation id and expected outcome
revision. The host accepts only an exact current terminal revision. Retrying an
already-recorded acknowledgement for that revision is idempotent; a stale
revision fails without changing state.

Audit idempotency is keyed by organization and the host-generated operation
incarnation (operation id plus immutable start time). Acknowledgement audit
idempotency also includes the outcome revision. This keeps exact retries
idempotent without letting a deliberately reused historical client UUID hide a
later operation.

### Presentation authority

The browser surfaces every host-reported unacknowledged operation and hides
every host-reported acknowledged operation. It does not:

- compare installed and target versions to infer remediation;
- persist a local dismissal;
- match an operation using only its target version; or
- derive a revision from mutable messages or timestamps.

An acknowledgement failure leaves the terminal outcome visible. An ambiguous
trigger remains locked only while the exact command id is unconfirmed and the
host cannot provide an authoritative status.

## Safety invariants

The refactor must preserve these existing guarantees:

1. Fleet never receives the Docker socket or root privileges.
2. Trigger admission remains single-flight, forward-only, and bound to the
   exact eligible release.
3. Browser cancellation cannot cancel an admitted mutation, while Fleet HA
   demotion still can.
4. Pre-activation work remains cancellable; migration-bearing activation is
   not canceled by updater shutdown.
5. The release is fully verified, prepared, and synced before teardown.
6. Only the proven pre-command rename window may restore the prior deployment;
   post-migration recovery remains forward-only.
7. HA role, peer-version, takeover, and application-restart checks remain in
   their current order.
8. State, logs, install roots, executables, socket paths, and archives retain
   their ownership, mode, no-symlink, size, and retention protections.

## Validation

- Exact-id retry admits one host operation and produces one trigger audit.
- Exact-id replay returns the retained host operation even after the offer or
  installed version changes; fresh ids still require current eligibility.
- Reusing an id with another target is rejected.
- A lost browser response recovers only the exact operation id.
- Reloading during admission or the exact operation's active lifetime
  preserves the conflicting-operation lock for the same authentication
  session.
- A rewritten terminal outcome advances its revision and rejects an old tab's
  acknowledgement.
- Acknowledgement retries produce one audit for the exact revision.
- Historical UUID reuse produces a new trigger and acknowledgement audit for
  the new host-generated operation incarnation.
- Reload acknowledges a successful outcome before replacing the browser
  document and leaves it visible when acknowledgement fails.
- Host-unavailable acknowledgement leaves the outcome visible.
- Caller cancellation and HA demotion retain their existing opposing
  semantics.
- Updater manager, local HTTP protocol, Fleet domain/handler, client hook, and
  Updates page tests pass along with generated-code and repository lint checks.

## Follow-up architecture seams

Once this contract is stable, the host manager can be split without carrying
browser or protocol ambiguity into the new boundaries: operation store,
release bundle preparation, deployment swap, topology activators, trusted
filesystem operations, logs, startup repair, and an optional binary
supervisor. Packaged deployment can then move to prebuilt images and one
mutation owner independently of the operation protocol.
